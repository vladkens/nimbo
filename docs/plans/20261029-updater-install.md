# Updater install, the Sparkle way

Goal: `install` no longer swaps the app while it runs. It starts the new version's binary from the staging folder as a separate installer, returns, and the app quits; the installer waits for the old process to end, swaps the whole app in one step, starts it with the old arguments, removes what is left and exits. That drops the instance wait, `NIMBO_RELAUNCH`, its token, `Claim::Replaced`, the 60 s cap, the per-file Windows swap, the per-file `.nimbo-old` names, the kept folders and the launch-time cleanup. Decided by the person 2026-10-29, on PR #48 (branch `feat/updater`).

## Decisions

- **Flow.**
  - `install(staged)` starts `<new binary> --nimbo-install <old pid> <new> <target> -- <the app's arguments>` and waits up to 10 s for the installer's mark file `ready` in the staging folder (killing the installer and returning `Err` if it never comes, nothing swapped). Then `Ok`, and the app must quit within 30 s. The staging folder now belongs to the installer: `Staged`'s drop no longer removes it. The path `<new>` is passed explicitly rather than derived from `current_exe` (on Linux that is inside the AppImage's mount), and must be under a `.nimbo-update-` folder beside `<target>`, else the installer exits with status 2.
  - The installer is detached from the old app: on Unix its own process group (`process_group(0)`) with stdio on `/dev/null`, so a terminal's hangup doesn't reach it; on Windows `DETACHED_PROCESS | CREATE_NO_WINDOW`, with `CREATE_BREAKAWAY_FROM_JOB` tried first and dropped if the job refuses it.
  - Where it runs from: macOS, the staged bundle's binary; Linux, the staged AppImage; Windows, a copy of the new exe alone at `<staging>\<exe name>`, because a folder holding a running exe can't be renamed. The rule that follows: a Windows app's exe must start with no DLLs from its own folder (wavo-app ships `Wavo.exe` alone).
  - `nimbo::update::finish()` is called first in `main`, before argument parsing and before any AppKit, window or instance call, so install mode never shows a Dock icon, a window or a console. With `--nimbo-install` as the first argument it runs the steps below and exits (status 0, or 1 on failure). Otherwise it does nothing but the one check in **Failure** below.
  - Install mode:
    1. Sets its working directory to the target's parent: Explorer starts an app with its own folder as the working directory, which would block the rename. Then writes `ready`.
    2. Waits until the old process has ended, for at most 30 s. On Unix it waits while `getppid()` is the old pid: the installer is that process's child, so a reused pid can't fool it. On Windows it calls `OpenProcess(SYNCHRONIZE)` and `WaitForSingleObject` with the cap. Past the cap it removes the staging folder and exits 1, changing nothing.
    3. Swaps (see **Swap**), then starts the installed app with the original arguments. On macOS that is `/usr/bin/open -n -g <target> --args …`, so LaunchServices starts it in launchd's environment and it is its own responsible process for TCC, without taking the focus. On Windows it spawns `<target>\<exe>`; on Linux it spawns `$target` with `APPIMAGE`, `APPDIR`, `ARGV0` and `OWD` removed from the environment, which the runtime sets again.
    4. If the swap or the start fails, it undoes the swap and starts the restored old app with the same arguments, so the user still has the app.
    5. Removes the old copy and the staging folder, each with `uninstall::remove` (it retries while a file is busy for 5 s), and exits.
- **Swap: the whole app, one step.** The staging folder is beside the target on every OS, now in the parent of the app's folder on Windows too (`%LOCALAPPDATA%\Programs`), so `beside` loses its Windows case and the writability check covers that parent.

  | OS | target | swap | undo |
  |---|---|---|---|
  | macOS | the `.app` | `renamex_np(new, target, RENAME_SWAP)`, the atomic exchange Sparkle's `SUFileManager` uses on APFS; on `ENOTSUP` (HFS+), target renamed to `.<name>.nimbo-old`, then new renamed in | the same exchange again, or the two renames reversed |
  | Windows | the app's folder | target renamed to `<name>.nimbo-old`, new renamed in, each with `uninstall::retry` (antivirus and Explorer hold the folder briefly) | the two renames reversed |
  | Linux | the AppImage | `link(target, .<name>.nimbo-old)`, then `rename(new, target)`, which replaces atomically | `rename(old, target)` |

  On macOS and Linux a crash mid-swap never leaves the app missing. On Windows the gap is the time between two renames. If the installer is killed, its staging folder and an old copy can be left; the next `download` removes any `.nimbo-update-*` folder of an ended pid and any `.<name>.nimbo-old` beside the target before it stages a new one, which replaces `tidy` on every launch. Whatever the app keeps inside its own folder is replaced with it (no portable data in the app's folder), and files a release drops are gone with the old copy.
- **Failure.** The installer has no UI and the old app is gone, so it writes its error to `.<name>.nimbo-update-error` beside the target before it starts the restored app. In normal mode `finish()` returns that error once, `Option<io::Error>`, and removes the file: one `exists` per launch. This is a small deviation from "does nothing in normal mode". Without it, an app that installs on its own would hit the same failing install on every check without anyone seeing why.
- **instance.rs** goes back to main's version: `claim_until`, `relaunch`, `relaunched`, `key`, `CLAIMED`, `RELAUNCH`, `TOKEN`, both waits and their three tests go. Windows' `pipe_path` hashes inline again, and `alive` leaves both platform instance files. The wait moves to `platform::update::wait_exit(pid, cap) -> bool`.
- **macOS designated requirement: Security.framework, recommended.** `SecStaticCodeCreateWithPath` for both bundles, `SecCodeCopyDesignatedRequirement` of the running one, `SecStaticCodeCheckValidityWithErrors(new, kSecCSCheckAllArchitectures, req)` with the error's description, as Sparkle's `SUCodeSigningVerifier` does. It uses `objc2-security` 0.3.2 with `CSCommon`, `SecBase`, `SecCode`, `SecStaticCode` and `SecRequirement`: measured 21 → 22 crates on aarch64-apple-darwin (bitflags is already there), within the objc2 family, about +15 lines over the `codesign` text parsing it replaces. Why not CI only: only the running app sees both builds. A CI check can't stop a release signed with another identity (or ad hoc) from reaching users and silently dropping their microphone and Accessibility grants, nor stop a dev build being installed over an installed one. The feed's Ed25519 key stays the security gate, and the requirement guards the grants.
- **Signature inside the feed: yes, recommended.** The last line is `sig <128 hex>`, Ed25519 over every byte before that line; it must be the last line and appear once, else `InvalidData`. One fetch, one file to upload, no race between two assets, so the second fetch, the retry, `sig()` with its query handling and its test, and the `/race.txt` server route all go (about −15 code lines and −20 test lines). `scripts/update-feed.py` appends the line instead of writing `update.txt.sig`.
- **HTTP: keep ours (~215 code lines in three files).** Measured with nyquest 0.5.0 and nyquest-preset 0.5.0 (`blocking`, and the same with `blocking-stream`) in a scratch copy of Cargo.toml: aarch64-apple-darwin 21 → 40, x86_64-pc-windows-msvc 6 → 37, x86_64-unknown-linux-gnu 4 → 38. What nyquest covers:
  - blocking: yes;
  - redirects: on or off only, with no limit and no https-only rule;
  - a byte limit: `max_response_buffer_size` applies only to `bytes()` and `text()`, not to streaming;
  - progress: none of its own, only by counting `into_read()`;
  - the system proxy on Windows: yes, but through WinRT `Windows.Web.Http` and the `windows` crate (about 12 crates), not WinHTTP;
  - Linux: `curl-sys` and `openssl-sys` link libcurl and OpenSSL at build time, which breaks "loaded at run time" on Linux.

  It would also need its backend registered at startup.
- **wavo-app API change** (its `feat/updater` worktree):
  - `main`: `if let Some(e) = nimbo::update::finish() { … }` as its first line, before `attach_console` and `Cli::parse` (clap would reject `--nimbo-install`); the error goes to the updater's status.
  - `app.rs`: the `Claim::Replaced` arm goes. `install_staged` waits for no dictation first, then calls `install` and quits as soon as it returns `Ok`. `INSTALLED_QUIT` (50 s) and `quit_installed` go: the installer waits 30 s at most. An `Err` from `install` now covers only the spawn and the 10 s handshake. Errors from the swap or the start come back through `finish()` on the next launch.
  - CI (`.github/workflows/main.yml`): uploads `update.txt` alone, its `sig` line made by the new `update-feed.py`, with no `.sig` asset.
- **Lines** (code as `make size` counts it):
  - About 240 out: in `update.rs`, `tidy`, `leftovers`, `olds`, `pairs`, the per-file `swap` and `undo`, `put`'s half-swapped error, `Folder::keep` and the kept logic, `sig()` and the retry; instance.rs +57 back to 0; both `alive`; the macOS `relaunch` with its process polling and 35 s timeout; `NIMBO_RELAUNCH` in each platform file; the example's `Replaced` arm, `relaunched` and `TIDY`; tray's `Replaced` arm.
  - About 130 in: `finish` with its argument parsing, the wait, the swap and the start, `install`'s spawn and handshake, the error note, the inline `sig` line, `wait_exit` on each OS, `renamex_np`, and the Security calls.
  - Net about −110 of the PR's ~860 code lines. Tests about −250 / +130.
  - `update` budget 600 → 400 if it fits; the others stay.
