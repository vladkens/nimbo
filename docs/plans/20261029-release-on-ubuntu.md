# Release on Ubuntu

Goal: an app's release files (the macOS `.app` and DMG, the Windows setup, the AppImage and `.deb`, the feed) all made and signed in one Ubuntu publish job of vladkens/actions' rust-publish, from the bare binaries the build jobs leave, with no macOS or Windows runner in the publish step. Agreed with the person 2026-10-29, from the draft of the same day.

## Decisions

- `scripts/pack.py` stays one file: wavo-app fetches it as one. Plain `python3` 3.9+ with the standard library, doctested under `python3` and `/usr/bin/python3`.
- The build jobs only run `cargo build` and copy the binary to `target/distrib/<triple>/<bin>[.exe]`; pack.py isn't used there.
- The Windows exe's icon, version and manifest are written by pack.py's own PE resource code in the Ubuntu publish job: no rcedit, no npm, no build.rs.
- No Wine anywhere.
- sips, iconutil, vtool and lipo give way to pure Python on every OS: a PNG codec, the `.icns` and `.ico` writers and a Mach-O reader.
- The `.icns` writes 16 and 32 px as `ic04` and `ic05` (ARGB), as iconutil does, not as PNG in `icp4` and `icp5`: macOS 27's iconutil reads those as noise (checked 2026-10-29).

## Stages

- [x] 1. In pure Python: PNG decode and encode, the alpha-weighted resize and the tile crop (from wavo-app's build.rs), the `.icns` (ic04 ic05 ic07–ic14) and `.ico` (16–256) writers, a Mach-O reader (the arch, thin and fat, and the minimum macOS), and `exe_resources`, which writes the exe's RT_GROUP_ICON and RT_ICON, RT_VERSION and RT_MANIFEST into its `.rsrc`, merged with the linker's. Wired into today's `app`, `dmg` and `setup`. Checked on the `counter` example cross-built for x64 and arm64 Windows.
  - Result: `scripts/pack.py` 945 → 1,680 lines (the images ~310, Mach-O ~70, the exe's resources ~360), doctested under `python3` 3.13 and `/usr/bin/python3` 3.9. The PNG decoder matches Pillow on 45 files using all five filters and every supported colour type; the `.icns` round-trips through iconutil; the Mach-O reader matches lipo and vtool on thin and fat binaries. `exe_resources` on `counter.exe` (cargo xwin, x64 and arm64, and x64 with lld-link's embedded manifest, `.rsrc` before `.reloc`): llvm-readobj and pefile read the icon group (6 PNG icons), the version, the manifest (ours replacing lld-link's), the same imports and base relocations, a correct checksum, and a second run gives the same bytes. Not yet run on real Windows.
- [x] 2. macOS on Linux: `app` signed by rcodesign, the DMG by `mkfs.hfsplus`, libdmg-hfsplus's `hfsplus` and `dmg`, then rcodesign's notarization and staple; codesign and hdiutil stay for local Mac builds.
  - Result: `scripts/pack.py` +194/−10. Off macOS, `app` is signed by rcodesign (apple-codesign 0.29.0, sha256-pinned for x86_64 and aarch64 Linux musl and aarch64 macOS; the x86_64 Linux hash checked against its release's SHA256SUMS) with `--code-signature-flags runtime`, the entitlements and `--for-notarization` from APPLE_CERTIFICATE, turned into a 0600 PEM by OpenSSL 3 (`-legacy` as a fallback), else ad hoc. The DMG is an image of `du` × 1.1 + 4 MiB, `mkfs.hfsplus -v <Name>`, `hfsplus` `mkdir` and `addall` of the app and `symlink /Applications /Applications`, then `dmg --compression lzma build`; rcodesign signs it, and with the three API secrets `notary-submit --staple --max-wait-seconds 1200` from a 0600 key JSON. A `v*` label with a secret missing fails; dev without them stays ad hoc and the DMG unsigned. `dmg` and `hfsplus` come from `$NIMBO_TOOLS`; `LIBDMG`, the tools-<date> release, is a placeholder that fails until vladkens/actions' tools.yml has run. `plutil -lint` is gone (plistlib writes the plist). Checked on this Mac with the Linux path forced, libdmg-hfsplus e18579b39195 built by plain cmake (no flags; the SDK's zlib, bz2 and lzma) and a stand-in `mkfs.hfsplus` that runs `newfs_hfs` on the image attached as a raw disk: the counter example's app, ad hoc and signed by a self-made certificate from both a modern and an RC2 (`-legacy`) .p12, passes `codesign --verify --strict` (flags runtime, the entitlements, its DR `identifier … and certificate root`); the DMG (ULMO, 469 KB against UDZO's 975 KB) passes `codesign -dv` and `hdiutil verify`, and `hdiutil attach -nobrowse -readonly` shows `Counter.app`, still valid, and `Applications -> /Applications`. - [x] 3. NSIS in place of Inno Setup, built by `makensis` on Ubuntu, and update.rs's Windows setup run as `/S`.

The Inno code is gone: `compiler`, `script`, `esc`, `q`, `arg`, `ARCHES` and their doctests; update.rs runs the setup `/S` (b7e290b). Checked: the `.nsi` doctested for x64 and arm64 under `python3` 3.13 and `/usr/bin/python3` 3.9; `setup` of the counter for x64 and arm64 with a stand-in makensis that checks its arguments and the files and writes the packed exe as `setup.exe`. - [x] 4. `release <dir> --label <dev|vX.Y.Z> [--tag vX.Y.Z]`: reads `<dir>/<triple>/<bin>[.exe]` and writes the release files at `<dir>`'s top level, plus update.txt only with a tag, its URL `<Cargo.toml repository>/releases/download/<tag>/`.
  - Result: `scripts/pack.py` 1,895 → 2,026 lines (+161/−30), 82.6 KB. `release` takes only `<dir>/<triple>/<bin>[.exe]` of the six triples, a regular file, no link, that is a Mach-O (one slice), PE or ELF of that OS and arch; anything else there, an empty folder or no folder exits naming what it refused. Per triple, at `<dir>`'s top level: the `.app` then the DMG, the setup, or the AppImage and `.deb`; then, with `--tag`, update.txt signed by UPDATE_KEY (required), its urls `<repository>/releases/download/<tag>/<file>`, the AppImage for Linux. A `v*` label must be `v<version>` (Cargo's, by `cargo metadata --no-deps` of `--manifest`) and needs the secrets; `--target`, `--bin`, `--app`, `--out` and a second folder are refused, `--tag` off `release` too. `Config` reads `repository`. The module docs describe the CI: three build jobs leave bare binaries in `target/distrib/<triple>/`, the Ubuntu publish job (`apt-get install nsis hfsprogs`) runs `release` with the secrets in its env. `dist` stays; nothing else went unused. Checked on this Mac with the Linux path forced, libdmg-hfsplus from `$NIMBO_TOOLS`, the stand-in `mkfs.hfsplus` of stage 2, and stand-ins for makensis, appimagetool and dpkg-deb: over the counter for aarch64 macOS (built here), x86_64 Windows (cargo xwin) and x86_64 Linux (cargo zigbuild), then also arm64 Windows and aarch64 Linux, it writes the DMG (`hdiutil verify` passes, it attaches with `Counter.app`, valid, and `Applications`), the setups (their exe has the icon, version and manifest), the AppImages and `.deb`s, and with `--tag` and a test key an update.txt whose sizes and SHA-512s match the files and whose signature openssl verifies. Refused as they should be: a file at the top, an extra file beside the binary, an unknown triple, a linked binary or folder, an exe without `.exe`, a Linux binary as the Windows exe, the arm64 Mac binary under x86_64, an empty or missing folder, `--tag` without UPDATE_KEY, `v0.3.2` for 0.3.1, `v0.3.1` without the Apple secrets. Not run: makensis, appimagetool, dpkg-deb and `mkfs.hfsplus` themselves, signing and notarization in `release`, and Ubuntu.

## Result

All four stages done and checked locally on this Mac (the Linux path forced, stand-ins for makensis, appimagetool, dpkg-deb and `mkfs.hfsplus`): `scripts/pack.py release` makes every release file from the build jobs' bare binaries, the images, the Mach-O reader and the exe's resources in pure Python, NSIS in place of Inno. The plan stays here until the proofs pass: the real tools and notarization on Ubuntu (wavo-app's CI) and the setup on real Windows (the Windows VM).

Then made smaller, with no feature lost: `scripts/pack.py` 2,028 → 1,591 lines, `src/png.rs` 503 → 457 lines of code (core 3,948 → 3,902 of 4,000). The exe's resources are append-only: a new last `.rsrc` of our id-only tree, data directory 2 pointing at it, CheckSum 0, the linker's left unused (llvm-readobj on the counter for x64, arm64 and x64 with lld-link's manifest: ours is the one pointed at, the imports, relocations, debug, load config, unwind and TLS as they were); the manifest keeps Common Controls 6 and drops dpiAware (nimbo sets PerMonitorV2 itself). The commands are `release`, `app --bin`, `feed` and `feed-key`; `release` takes `<dir>/<triple>/<bin>[.exe]` of the six triples as it finds them, the Mach-O reader is LC_BUILD_VERSION's minos of a thin binary, and on a Mac codesign signs with a Developer ID or "<Name> Local Signing", never timestamped. Both PNG readers take 8-bit RGB, RGBA and a palette with its tRNS; Rust's panics on anything else, as `Png::rgba` did, without the CRC, Adler-32 and size checks. The icns's ic10 is the icon's own file when it is 1024 px.

Then the DMG's window, the simplest Finder layout: pack.py writes the volume's `.DS_Store` itself (~45 lines, the records dmgbuild writes, the format from its ds_store package, MIT), on both paths: a 640×400 window with no toolbar, sidebar or background, the app and the Applications link as 128 px icons side by side. Its leaf is byte for byte the one ds_store writes for the same records, and ds_store reads the file back; the counter's DMG from the Linux path and from hdiutil opened in Finder on the macOS 27 VM as that window.
