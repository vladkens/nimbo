# System change notices: audio inputs and the lid

Goal: an open window and the tray follow the hardware while the app runs. Today an app reads its audio inputs (cpal), `nimbo::hardware::transport` and `nimbo::hardware::lid_closed()` once, when its window opens, so in wavo-app a mic plugged in or out, a Bluetooth headset connecting, the system default input changing or the lid opening or closing only show once the window opens again (its tray menu is right only because it reads again each time it opens). nimbo gives (1) a notice on one general channel for system changes (`Event::System`), on the main thread and coalesced per kind (a burst gives one), when the input device list or the default input changes and when the lid opens or closes, and (2) a documented way for an app with a tray and open windows to redraw from it without polling, within the borrow rules (state only through `try_borrow*` and the helpers; a busy window gets it later, never drops it), with an example and headless tests that fake the notice.

## Decisions

### How others give apps system changes (read 2026-10-30)

- Apple has two forms. A *value* the views read, pushed to them and re-rendering them: `@Environment(\.colorScheme)` ([EnvironmentValues.colorScheme](https://developer.apple.com/documentation/swiftui/environmentvalues/colorscheme), macOS 10.15+), and with Observation a view "updates … only when an observable property changes and the view's body reads the property directly" ([Migrating to the Observable macro](https://developer.apple.com/documentation/swiftui/migrating-from-the-observable-object-protocol-to-the-observable-macro); `withObservationTracking(_:onChange:)` "tracks access to any property within the apply closure", macOS 14+). And a *notice*, on one channel with named notifications that an observer adds itself for: `NotificationCenter`, e.g. `AVCaptureDevice.wasConnectedNotification` / `wasDisconnectedNotification` for cameras and microphones (macOS 10.7+, delivered on the queue the observer names, `.main`), `NSApplication.didChangeScreenParametersNotification`, `NSWorkspace.didWakeNotification`. The device list itself isn't an environment value: an app observes it and reads it again.
- Flutter: one observer interface for every system change, a method per kind (`didChangePlatformBrightness`, `didChangeMetrics`, `didChangeLocales`, `didChangeAppLifecycleState`, `didChangeAccessibilityFeatures`, `didChangeTextScaleFactor`), added with `WidgetsBinding.instance.addObserver` ([WidgetsBindingObserver](https://api.flutter.dev/flutter/widgets/WidgetsBindingObserver-class.html)).
- Qt: an object per area with signals; monitoring comes with the object: `QMediaDevices` emits `audioInputsChanged()` on a plug or a default change ([QMediaDevices](https://doc.qt.io/qt-6/qmediadevices.html), Qt 6.12); `QGuiApplication::screenAdded`. GTK: signals on the object, `GdkDisplay::monitor-added` ([since 3.22](https://docs.gtk.org/gdk3/signal.Display.monitor-added.html)). Electron: an emitter per module, `screen`'s `display-added`/`display-removed`/`display-metrics-changed` (["cannot be used until the ready event"](https://www.electronjs.org/docs/latest/api/screen)), `powerMonitor`'s `suspend`, `resume`, `on-ac`, `on-battery`, `lock-screen` ([powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor)).
- So there are two forms. A value the toolkit keeps current and the views read (colour scheme). A notice that says "read again", for state the app reads itself, often through another library (devices through AVFoundation, Qt Multimedia or cpal). nimbo already has the first (`Event::Appearance`). It lacks the second, and Flutter's single observer and `NotificationCenter`'s single channel show how to keep it one channel as kinds are added.

### The API

- **One channel for every system change:** `Event::System(system::Change)` to every open window, and a hook given with the subscription for the app outside its windows (the tray, an app-wide model): `Main::watch(kinds: &[Change], f: impl FnMut(&mut Main, Change) + 'static) -> Result<(), String>`, as `Main::serve` takes its handler. The same `Change` goes through the same path, first the hook, then the windows. `Change` is a `#[non_exhaustive]` enum of kinds without data: `AudioInputs` (an input came or went), `DefaultInput`, `Lid` now; `Displays`, `Power`, `Network`… later, so an app's `match` keeps a `_ =>` arm and a new kind breaks nothing. A notice says what to read again (cpal, `hardware::transport`, `hardware::lid_closed()`), not the new value, as `NotificationCenter`'s device notices and Qt's `audioInputsChanged()` do. It can come when nothing the app sees changed (macOS's `'dev#'` and Windows' added/removed/state changes cover outputs too; a Linux sink's `.monitor` source), so the docs say "read again".
- **Watching is opted into per kind:** `Main::watch` starts each kind not yet watched, until the loop ends; a second call adds kinds and replaces the hook. `Err` names each kind the OS refused (e.g. `AudioInputs: libpulse.so.0 not found`); the rest are watched. The windows get `Event::System` only for watched kinds; one that doesn't care returns false and isn't redrawn, as a Flutter observer ignores the methods it doesn't override. Rejected: watching started by the first read (`lid_closed()`, `transport()`), as Observation tracks what `body` reads. (1) The main reads, the audio devices, happen in cpal, which nimbo never sees, so the main case would need a call anyway. (2) Those reads are "from any thread", cheap and side-effect free (CLI paths and tests call them with no loop running); starting OS listeners, a libpulse thread or a system-bus subscription from them would be a hidden cost on whatever thread reads, with nowhere to deliver. (3) Observation re-tracks on every `body` and so stops by itself; nimbo would never stop. An explicit call, like `addObserver` or creating a `QMediaDevices`, is one line and says what the app pays for. Per-window tracking of reads made through `Ui` (`ui.lid_closed()`, redrawing only the windows that read it) could come later over the same channel if a cost shows; it doesn't now (a notice a window ignores costs one event call).
- **`Event::Appearance` stays as it is.** It is the *value* form: it carries the value (dark, accent); the runtime consumes it itself (the theme follows it, repeats are dropped); it's sent to a window before its first frame; and on macOS it's per window (`viewDidChangeEffectiveAppearance`: a window can have its own appearance), which is SwiftUI's environment. Folding it into the "read again" channel would lose the initial value and the per-window override and push the theme's job onto every app. A `Change::Appearance` for the hook (a tray drawing its own icon) can be added when an app needs it; nimbo's tray retints itself today.
- **Busy windows, one portable retry in `src/system.rs`:** each platform gives `send(id, ev) -> Option<bool>` beside its `with_app` (`None` when the window is busy up the stack or gone): macOS `view(id)`, not `busy()`, then `View::send`; Windows `with_window` with `send` and `sync_modal` (a live resize's or a menu's loop draws from its timer); Linux `try_borrow_mut`, `send`, `sync`. `system.rs` sends to every open window (`shell::windows()`) and tries the ids it missed again after 100 ms through `Proxy::after`, as Linux's `settings.rs` does for the appearance, until they take it or close. Nothing goes through `Window::with` (`None` while busy) and nothing waits on a platform queue that may never be flushed, so a notice is never lost. Rejected: a callback per kind (`hardware::watch(f)`): a hook per kind multiplies with every kind added.
- **The hook while it runs:** a delivery that comes while the hook runs (a nested loop up the stack: a dialog, a paste waiting) is queued and runs after it, as `shell::command` queues commands (`Hooks::queued`); the hook and its queue live in `shell.rs`'s `Hooks`, reset by `running()`.
- **Coalescing per kind, portable, in `src/system.rs`:** one `Watcher` struct (a single static instance; tests build their own, as they run in parallel) of atomics: `watched` and `pending` bit sets, per kind `first` and `last` (nanoseconds since a process epoch), and `scheduled`. Native callbacks, from any thread, call `system::notice(Change)`: an unwatched kind is ignored; `last` stored; the kind's bit `fetch_or`'d into `pending`, and when it was clear `first` stored and, unless a job is scheduled, `Proxy::after(250 ms)`. On the main thread the job clears `scheduled`, then for each pending kind asks a pure `due(first, last, now) -> Result<(), Duration>`: due 250 ms after the kind's last notice or 1 s after its first (a headset connecting gives several device and default changes over a second). A due kind's bit is cleared before it is delivered, so a notice during the delivery starts a new burst; kinds due together go out in the enum's order, each as its own hook call and window event; what isn't due posts the job again for the least wait. `watch` and `unwatch` clear the kinds' pending bits. At worst a burst is delivered early (a notice between its `fetch_or` and its `first` store reads an old `first`), never lost. Below, `DEVICES`, `DEFAULT_INPUT` and `LID` stand for `Change::AudioInputs`, `DefaultInput` and `Lid`. Nothing in a callback locks or waits: Microsoft's rule for `IMMNotificationClient` ([IMMNotificationClient](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient), updated 2024-02-22: "must be nonblocking … never wait on a synchronization object"). So Windows' `post` reads the shell's window from an atomic instead of today's `Mutex<isize>` `HOST`. The race this opens: a post that loads the handle just before the loop ends sends to a window being destroyed; `PostMessageW` fails and the job is dropped, or the message is lost with the window, and its closure leaks once at exit. That is acceptable, because `Proxy` drops work after the loop anyway. It's written in `HOST`'s doc.
- **Lifetime:** what `Main::watch` starts runs until the loop ends (`shell::running` unwatches everything). An app that watches nothing pays no listener, thread or bus connection. `nimbo::run` (one window, no `Main`) doesn't get it now; it's a follow-up if an app needs it. Registration is synchronous on the main thread so `Err` comes back; task 2 measures the cold start (the first CoreAudio call connects to coreaudiod). `src/hardware.rs` keeps the reads; `src/system.rs` (the kinds, the watcher, delivery to the windows) counts in `app/shared` (`PARTS` in `scripts/size.py`).

### Per OS
- **macOS** (`src/platform/macos/app/hardware.rs`, declared by hand as the file already does; no new crate and no objc2 feature):
  - Audio: `AudioObjectAddPropertyListener(kAudioObjectSystemObject = 1, &{'dev#' | 'dIn ', 'glob', 0}, proc, null)`, removed with `AudioObjectRemovePropertyListener`. The proc listener, not the block one: no block to keep alive, symmetric removal, and the callback only calls `notice`, so its thread doesn't matter. The SDK's `AudioHardwareDeprecated.h` says the HAL attaches its notification handlers to `CFRunLoopGetMain()` since 10.6 (`kAudioHardwarePropertyRunLoop`); the thread the proc actually runs on is logged once in the VM check and written into the code's comment. The header also says a listener may be told of addresses it didn't ask for, so the proc notices the kinds of the addresses it is given. Source: MacOSX.sdk 27.0 (Xcode 27.0, read 2026-10-30), `CoreAudio.framework/Headers/AudioHardware.h` (`AudioObjectAddPropertyListener`, `AudioObjectPropertyListenerProc`, `kAudioHardwarePropertyDevices = 'dev#'`, `kAudioHardwarePropertyDefaultInputDevice = 'dIn '`).
  - Lid: `IONotificationPortCreate(0)`, `IONotificationPortSetDispatchQueue(port, main queue)`, `IOServiceAddInterestNotification(port, IOPMrootDomain, "IOGeneralInterest", cb, null, &notifier)`; `cb` sets `LID` for `kIOPMMessageClamshellStateChange` = `iokit_family_msg(sub_iokit_powermanagement, 0x100)` = `0xE003_4100` (its argument holds `kClamshellStateBit` 1 and `kClamshellSleepBit` 2; the state is read again by `lid_closed()`, as today). Released with `IOObjectRelease(notifier)` and `IONotificationPortDestroy`. Source: the same SDK, `IOKit.framework/Headers/pwr_mgt/IOPM.h` (the message, "delivered as a general interest notification on the IOPMrootDomain", sent before any sleep it causes), `IOKitLib.h`, `IOMessage.h`, `IOReturn.h` (`sys_iokit` `err_system(0x38)`, `sub_iokit_powermanagement` `err_sub(13)`).
  - `send(id, ev)` lives in `app/mod.rs` (re-exported by `shell.rs`'s existing `pub use super::app::{…}`), with `view` made `pub(super)`, as `platform/macos` is at its budget, 2500/2500.
- **Windows** (`src/platform/windows/app/hardware.rs`; windows-sys only, no new feature):
  - Audio: a static, free-threaded `IMMNotificationClient` (a vtable by hand; `AddRef`/`Release` constant, as it lives for the process; `QueryInterface` for IUnknown and `7991EEC9-7E89-4D85-8390-6C703CEC60C0`), registered with `IMMDeviceEnumerator::RegisterEndpointNotificationCallback` (slot 6; `Unregister…` slot 7) on the main thread, the enumerator kept until the loop ends. COM on the main thread: a tray app watches before any window exists, while OLE (an STA, for drops) starts lazily on the first window (`files::register`); a COM init of our own in the MTA kept on that thread would make `OleInitialize` fail with `RPC_E_CHANGED_MODE` and `RegisterDragDrop` with it. So the same once-per-thread helper, split out of `files::register` as `files::ole()`, runs before `CoCreateInstance`: the enumerator is free-threaded ("Both") and its callbacks come on the audio service's threads whatever our apartment. The slots, in `mmdeviceapi.h`'s order (checked against windows-rs 0.58's `IMMNotificationClient_Vtbl`): 3 `OnDeviceStateChanged`, 4 `OnDeviceAdded`, 5 `OnDeviceRemoved` → `DEVICES` (a Bluetooth headset's endpoints go ACTIVE/UNPLUGGED/NOTPRESENT as it connects; jack and USB plugs too); 6 `OnDefaultDeviceChanged(flow, role, id)` → `DEFAULT_INPUT` when `flow == eCapture (1)`, for any role (one call per role, coalesced; `id` is NULL when no input is left); 7 `OnPropertyValueChanged` ignored (frequent). The callbacks come on the audio service's threads, not ours ([Device Events](https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-events), updated 2025-03-11), and must never call `Register…`/`Unregister…` or release the last reference.
  - Lid: `RegisterPowerSettingNotification(host, &GUID_LIDSWITCH_STATE_CHANGE, DEVICE_NOTIFY_WINDOW_HANDLE)` on the shell's hidden window from `watch(Lid)` only, so `lid_closed()` on Windows is `None` until the lid is watched (and on a desktop), then known; `WM_POWERBROADCAST` with `PBT_POWERSETTINGCHANGE` gives a `POWERBROADCAST_SETTING` whose `Data` DWORD is 0 closed, 1 open. The value goes into an atomic `lid_closed()` reads. The first value only sets it; a later different value sends `LID`. "The callback won't be called until a lid device is found and its current state is known" ([Power Setting GUIDs](https://learn.microsoft.com/en-us/windows/win32/power/power-setting-guids), updated 2025-07-16), so a desktop stays `None`. The GUID is declared by hand (`BA3E0F4D-B817-4094-A2D1-D56379E6A0F3`, in windows-sys under `Win32_System_SystemServices`, which isn't enabled); `RegisterPowerSettingNotification` and `POWERBROADCAST_SETTING` come from the enabled `Win32_System_Power`. Unregistered with `UnregisterPowerSettingNotification`. [RegisterPowerSettingNotification](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerpowersettingnotification), updated 2025-07-01.
  - `send(id, ev)` lives in `app/shell.rs` beside `with_app`.
- **Linux** (no build-time C; dlopen'd and GDBus):
  - Audio: **libpulse** (`libpulse.so.0`, dlopen'd through `dl.rs`) with `pa_threaded_mainloop` (no `libpulse-mainloop-glib` needed): `pa_context_connect(ctx, NULL, PA_CONTEXT_NOFAIL | PA_CONTEXT_NOAUTOSPAWN (3), NULL)`: with no server yet the context waits in `CONNECTING` (not an error; only a missing `libpulse.so.0` is `Err`), and a server that dies after `READY` makes it `FAILED`, so the state callback, on pulse's thread, lets it go and connects a new one; on `PA_CONTEXT_READY` `pa_context_subscribe(PA_SUBSCRIPTION_MASK_SOURCE (0x2) | PA_SUBSCRIPTION_MASK_SERVER (0x80))`. A source `NEW (0x00)` or `REMOVE (0x20)` (facility `0x1`) sets `DEVICES`; a source `CHANGE (0x10)` is ignored (volume). A `SERVER (0x7)` event runs `pa_context_get_server_info` and sets `DEFAULT_INPUT` only when `default_source_name` differs from the last one (the server event also comes for the default output). Every `READY` after the first (a server restart) sets `DEVICES`. It speaks to PulseAudio and to PipeWire through `pipewire-pulse` (Ubuntu 22.10+, Fedora 34+), so it covers USB and jack inputs, Bluetooth headsets (BlueZ nodes become sources), virtual sources and the user's default. Callbacks on pulse's own thread call `notice`. Constants: `pulse/def.h` and `introspect.h` (`pa_server_info`'s layout, declared by hand: four strings, `pa_sample_spec` of 12 bytes, then `default_sink_name`, `default_source_name`) from [PulseAudio master](https://gitlab.freedesktop.org/pulseaudio/pulseaudio/-/blob/master/src/pulse/def.h), read 2026-10-30.
  - Rejected for audio: udev's `sound` subsystem through a dlopen'd libudev only sees ALSA cards (USB, HDMI, a jack), with no Bluetooth headset (BlueZ makes no card) and no default input (a sound-server notion); native PipeWire (`libpipewire-0.3`) does `pw_core_get_registry` and `pw_registry_add_listener` as static inline method-table macros, so it would be fragile by dlopen and Pulse already reaches it. Left uncovered: ALSA-only systems with no sound server, and JACK alone (no notice; the app reads again on open as today).
  - Lid: **UPower over GDBus on the system bus** (a new `dbus::system()`, `G_BUS_TYPE_SYSTEM = 1`, beside `session()`): subscribe to `org.freedesktop.DBus.Properties.PropertiesChanged` from `org.freedesktop.UPower` on `/org/freedesktop/UPower`, `LID` when the changed set holds `LidIsClosed`; `lid_closed()` reads `LidIsPresent` and `LidIsClosed` with `G_DBUS_CALL_FLAGS_NO_AUTO_START` (a read never starts `upowerd`) in one `GetAll` call: a synchronous round trip on the system bus, about a millisecond, at most its 500 ms timeout when the bus hangs (documented on `lid_closed`); `None` without a lid, without UPower, or off the bus. Today it is `None`. Not logind's `LidClosed`: it emits `PropertiesChanged` only since systemd 256 (commit `501d8b8bc6`, "logind: Mark LidClosed property as 'emits change'", 2024-01-03; v255's `logind-dbus.c` has `SD_BUS_PROPERTY("LidClosed", …, 0, 0)`), and Ubuntu 24.04 ships 255; nor does logind tell a desktop from a closed-lid-less machine. UPower's `LidIsClosed` and `LidIsPresent` come from gdbus-codegen's exported daemon (`up_exported_daemon_set_lid_is_closed` in `src/up-daemon.c`, [UPower master](https://gitlab.freedesktop.org/upower/upower/-/blob/master/src/up-daemon.c), read 2026-10-30), so they emit on change. Left uncovered: desktops without `upowerd` (minimal window managers).
  - `send(id, ev)` lives in `app/shell.rs` beside `with_app`.
### Core, example, budgets

- **Core:** `Event::System(system::Change)` in `src/app.rs`; `Runtime::event` gives it to the app as it does `FileDialog` (no pointer, keys or focus effect) and redraws when used. `Harness::event(Event::System(Change::Lid))` is the fake notice; nothing new in the harness.
- **The pattern, in `src/system.rs`'s module doc and the example:** the window's app reads its own data again on the kinds it shows and returns true; the hook updates what lives outside windows (the tray's menu or icon, an app-wide model the windows read in `view`). The hook runs before the windows' event, so a window reading the shared model sees it already updated.
- **Example:** a new `examples/system.rs` (named for the channel, so later kinds join it), a tray app with one window, apart from `tray.rs` so the counter stays the counter. It watches `AudioInputs`, `DefaultInput` and `Lid`. The tray's menu shows "Lid: Open/Closed/None" and "Audio changes: N" (and "Open Window", "Quit"); the window lists the lid, the count per kind and the last kind, in rows of one height. Each notice prints `system: Lid lid_closed=Some(true)` (or `AudioInputs`, `DefaultInput`) to stderr for the VM checks; `--shot` renders the window after one fake notice. The window reads the lid through a `fn() -> Option<bool>` field (`hardware::lid_closed` by default) so the tests fake it.
- **Crates:** none added, no new `windows-sys` or objc2 feature; the crate count is unchanged.
- **Budgets** (`scripts/size.py`, today → expected, measured as the code lands): `app/shared` 1660/1700 → ~1790, raise to 1800 (`src/system.rs`, the hook and its queue in `shell.rs`); `core` 3928/4000 → the variant only, fits; `app/macos` 1852/1900 → ~1930, raise to 2000; `platform/macos` 2500 unchanged; `app/windows` 1799/1800 → ~1930 (the COM object, power, registration, `send`), raise to 2000; `platform/windows` 2190/2200 → unchanged but for `HOST`; `app/linux` 2493/2500 → ~2700 (libpulse with reconnect, UPower), raise to 2800 if needed; `platform/linux` 3156/3200 → ~3170 (`dbus::system()`), fits. Each raise is recorded in the PR.

## API

```rust
// src/system.rs
/// A change in the system an app may show: read it again. Grows with new kinds.
#[non_exhaustive]
#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
pub enum Change { AudioInputs, DefaultInput, Lid }

// src/app.rs
pub enum Event { /* … */ System(crate::system::Change) }

// src/shell.rs
impl Main {
  /// Watches `kinds` (besides those watched already) until the loop ends: each change (a burst
  /// of one kind coalesced into one) runs `f` on the main thread, then reaches every open window
  /// as `Event::System`. `f` replaces an earlier one. `Err` names the kinds the OS refused; the
  /// rest are watched.
  pub fn watch(
    &mut self,
    kinds: &[Change],
    f: impl FnMut(&mut Main, Change) + 'static,
  ) -> Result<(), String>;
}

// in an app
let kinds = [Change::AudioInputs, Change::DefaultInput, Change::Lid];
let watched = main.watch(&kinds, move |_main, _change| tray.set_menu(&menu(&state)));
if let Err(e) = watched {
  eprintln!("system: {e}"); // the app's quiet status, no dialog
}

impl App for Recorder {
  fn event(&mut self, _cx: &mut Cx, ev: &Event) -> bool {
    match ev {
      Event::System(Change::AudioInputs | Change::DefaultInput) => { self.reload_devices(); true }
      Event::System(Change::Lid) => { self.lid = hardware::lid_closed(); true }
      _ => false,
    }
  }
}
```

Platform contract (in `src/platform/mod.rs`'s docs): `hardware::watch(kind: Change) -> Result<(), String>` per kind (the code in each `app/hardware.rs`; its listeners call `crate::system::notice(kind)` from any thread; the audio kinds share one registration) and `hardware::unwatch()`; `shell::send(id, ev) -> Option<bool>` (`None` when the window is busy or gone). Later kinds get files of their own.

## Risks

- CoreAudio's notification thread and run-loop mode aren't documented beyond the HAL using the main run loop: the proc only calls `notice`, so any thread works; if the HAL's source runs in the default mode only, a notice comes after the tray's menu closes (the menu reads again on open anyway).
- Cold start: the first CoreAudio call connects to coreaudiod; measured in task 2 and moved off the start if it costs.
- Windows COM: the object is static and lock-free, never released in a callback; `Unregister…` runs only from the main thread at the loop's end; OLE's STA starts first (`files::ole()`), so drops keep working when a tray app watches before its first window.
- Windows lid: `None` until `watch(Lid)`, and until Windows finds a lid; nothing on a desktop or in the VM, so the real lid is checked only on a laptop (unverified in this PR).
- Linux: UPower absent → no lid; libpulse absent → `Err` and no audio notices (the app reads again on open as today); no server yet → watched, noticed once one appears. `pa_server_info` is laid out by hand: the test checks the offsets against a struct filled in the VM (a real server's default source name read back). `pipewire-pulse` sending a server event when the default source changes is checked in the VM, not assumed.
- Sleep: closing a lid often sleeps the machine right after; the notice may come only after wake (macOS's message comes before the sleep it causes; the app sees it on wake).
- Spurious notices (outputs, monitor sources, a reconnect) cost an app's re-read; the coalescing caps them at a few per second.
- Budgets are near full in every platform part; the estimates may need another hundred somewhere (recorded in the PR).
