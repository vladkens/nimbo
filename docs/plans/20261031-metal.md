# Metal on macOS, opt-in, for the bunnies comparison

Status: in progress (2026-10-31), revised after an independent review (no blocker; its findings applied below) and the coordinator's decisions; one item waits for the person (the `agents.md` line, task 7). Branch `feat/metal` from origin/main 9ff1555.

Goal: a second renderer on macOS that draws nimbo's scene with Metal, built with the cargo feature `metal` and chosen at run time with `NIMBO_RENDERER=metal`, so the bunnies benchmark (hundreds to thousands of moving sprites) can run nimbo on the GPU beside egui, iced and GPUI. The CPU renderer stays the default on every OS and the reference for every pixel: the Metal path draws what the CPU path draws (within the tolerance below), paces and idles as it does, and costs at most a few MB more. Whether Metal stays after the benchmark, becomes a default, or goes is decided then, with its numbers.

Acceptance, all measured and written into `## Result`: (1) parity: every example's harness frame through Metal within max channel difference 2 of the CPU's, at most 0.5% of pixels differing (2% for `shapes`, with its up-scaled image and diagonal lines); (2) the window path in the macOS 27 VM (windows only there; the host runs headless tests only): `pace` ≥ 55 fps while the bar moves, no frame presented once still, idle wakeups no more than the CPU path's; a live resize shows no stretched or blank frame; (3) memory: idle footprint (`footprint`, `MTL_HUD_ENABLED=0`) of `counter`, `gallery` and `settings` at most 8 MB over the CPU path's in the same VM, compared fairly (below), and back within 1 MB of that idle value after a burst of frames ends; (4) `make check` and `make test` green with and without the feature; (5) the benchmark agent can build and run it with the commands in "For the benchmark".

## Why now

The benchmark in progress (2026-10-31) finds nimbo's worst case in "bunnies": in the macOS VM it drops under 60 fps between 300 and 1,000 sprites, while egui, iced and GPUI hold ~50+ fps at 10,000. The CPU raster's cost grows with covered pixels times sprites (bilinear sampling per pixel, `src/cpu/raster.rs` `image`); a GPU draws them as one instanced call. PR #64 made the renderer, the scene's internals and `Quad`'s fields crate-private, so a second renderer changes no public type.

What sgui measured (M2 host, `~/Code/sgui/docs/plans/20261017-backends.md`, results of 2026-10-18; the person's decision there: the CPU renderer by default everywhere, Metal an opt-in on macOS, pixel-checked against the CPU path, new drawing features land in the CPU renderer first; no Vulkan, D3D or GL):

- CPU time per full frame at 2560×1600: Metal (event + build + encode + submit) 0.02–0.27 ms median; the CPU renderer on 8 threads 0.38–2.32 ms; Metal's GPU time 0.14–1.93 ms median (p99 up to 6.4).
- Parity, the same scene through both in one process: no shot differed by more than 2 in any channel; the most pixels differing 1.5% (`primitives` at 2x: the up-scaled image's bilinear weights, the edges of diagonal lines and polylines), most shots under 0.1%.
- Footprint at rest (`MTL_HUD_ENABLED=0`), Metal / CPU: counter 29.3 / 20.7 MB, gallery 44.5 / 33.2, merge (100k) 114.7 / 102.4, trading 102.8 / 83.6; first frame within a few ms of each other. Gallery's breakdown: Metal 16 MB IOSurface (drawables) + 5 MB IOAccelerator + 15 MB malloc; CPU 12 MB IOSurface + 13 MB malloc.
- `~/Code/sgui/docs/native-vs-custom.md`: on macOS a Metal UI and a CPU-drawn one are within ~3–4 MB of each other (a bare NSWindow 20.0 MB, + Metal 24.9, + wgpu 26.4); a CAMetalLayer keeps ~3 drawables, ~12.7 MB each at 1100×752 @2x. GPU UIs on Windows and Linux cost an order of magnitude more (130–180 MB through wgpu), which is why they stay out of scope.
- `~/Code/sgui/docs/plans/20261017-wgpu.md`, memory levers: the device and atlases created lazily with the first window; atlases small and growing (its review chose 512² R8 and 256² RGBA to start) instead of 2048² R8 + 1024² RGBA (4 + 4 MB) up front; at most 2 drawables in flight unless 3 measure better; nothing renders while idle.

## The "4 CPU-renderer fixes" (found 2026-10-31)

The person's note (`~/Code/notes/nimbo/readme.md`, since e069c46 of 2026-10-22: "Metal (needs the 4 CPU-renderer fixes)") names the four changes to the rasterizer's maths made while porting sgui's CPU renderer into nimbo, in the review of PR #2 "port: core" (https://github.com/vladkens/nimbo/pull/2, Copilot's comments, fixed on that branch and squashed into a9b7ac2). sgui's `shaders.metal` predates them, so a Metal port that copied it would draw differently from nimbo's CPU path in exactly these cases:

1. Borders that meet or cross leave no fill (b2995ae): when the inner rect has no width or height, inner coverage is 0, not the 0.5 the SDF gives at its centre. Test `borders_that_meet_leave_no_fill`.
2. Empty quads draw nothing (6dfd780): `quad_bounds` is empty for a rect without positive width and height (an intersection that missed), shadow included, so no half-covered stripe. Test `empty_quads_draw_nothing`.
3. Uneven borders round the inner corner they border (74dfc08): the inner corner's radius and its two borders are picked by the quadrant around the inner centre (`ci`), not the outer one (`c`). Test `uneven_borders_round_the_inner_corner_they_border`.
4. A zero-length butt-capped segment draws nothing (6bf8798): `line_bounds` is empty for it; a round-capped one still draws a dot. Test `a_point_draws_only_with_round_caps`.

nimbo has all four in the CPU path since #2 (`src/cpu/raster.rs`: `quad_bounds`, `shade_quad`, `line_bounds`, and the four tests; a diff of sgui's `src/cpu/raster.rs` against nimbo's shows no other change to the maths). The other two fixes of that review (the scale in the tile hash seed, no padding after the last row) are the CPU renderer's own and don't concern a shader. This plan writes the shader from nimbo's `raster.rs`, with these four in it and a Metal twin of each test (task 2).

## What main has (checked 2026-10-31, 9ff1555)

- `src/scene.rs`: the same draw list as sgui's: layers with a clip, each with `quads` (`Quad`, `#[repr(C)]`, 96 bytes: rect, colour, border colour, radii, borders, blur, gradient, padding), `images` + `image_ids`, `lines` (`Segment`, 48 bytes), `glyphs` and `emoji` (`Sprite`, 48 bytes), drawn in that order per layer. Colours are straight sRGB; everything blends premultiplied in sRGB space (`BGRA8Unorm`, not `_sRGB`); image and emoji pixels are premultiplied RGBA.
- `src/cpu/`: `mod.rs` (prepare, 64-px tile hashes, damage, bands on a pool; `pixel_size` truncates a fractional size to whole pixels; `scissor` private; `sync` from the text system's uploads and the images queue, with `sync_pending` for a second renderer: `TextSystem::pending` is documented as "a second renderer reads them first"), `raster.rs` (the per-pixel maths, its comments naming the shader functions it mirrors: `quad_vs`, `quad_fs`, `pick_radius`, `rounded_rect`, `line_vs`, `line_fs`, `glyph_fs`, `image_fs`, the `linear` sampler; rounding half to even like a GPU's unorm store).
- `src/text/`: `Atlas::reset` (a new epoch) exists and `end_frame` uses it for a full atlas; the packer fills shelves across the full `ATLAS_SIZE` (2048) or `COLOR_ATLAS_SIZE` (1024) width, top down.
- `src/platform/macos/surface.rs` (118 code lines): `Presenter` draws into up to 3 IOSurfaces made lazily (a second while the window server reads the first, a third only while it reads both, `starved` when all are busy), each keeping the tile hashes of its frame, and sets the drawn one as the layer's `contents` in a `CATransaction`; an unchanged frame isn't shown again; on a size change all surfaces are dropped. Its tests run headless on `CALayer::new()`.
- `src/platform/macos/view.rs` (796 code lines, at the ~800 limit): `render()` builds the frame, then `presenter.renderer.sync(...)` and `presenter.present(...)`, synchronously, also from `setFrameSize:` inside the resize transaction (live resize never stretches); `View::new` reads `NIMBO_TRACE` and sets `presenter.renderer.transparent` for overlays; the link pauses in `on_tick` and in `after_frame`. State only through `try_borrow*`; busy frames are redone (`rewake`). The display link (`link.rs`) is untouched by this plan.
- `src/harness.rs`: `build()` (lines 362-368) runs a frame and `cpu.sync` after it (again after an applied resize); `render` draws with `cpu::Renderer::snapshot`; `Harness::set_transparent`; `Image { scale, pixels }` with BGRA `Pixels`.
- Budgets (`uv run scripts/size.py --check`): `platform/macos` 2861 / 2900, `core` 3962 / 4000, `text` 1188 / 1200; Metal code needs a part of its own. `scripts/size.py` counts `.rs` only, and its `module()` maps everything under `src/platform/macos/` to `platform/macos`.
- Crates (`cargo tree -e normal --target aarch64-apple-darwin --prefix none --no-dedupe | sort -u | grep -v '^nimbo ' | wc -l`): 13. Checked in a scratch copy: `objc2-metal` 0.3.2 adds 1 (14); its typed `newTextureWithDescriptor:iosurface:plane:` needs its `objc2-io-surface` feature, one more (15). `objc2-metal` with the features below builds in ~1.5 s. `objc2`'s `build.rs` only sets cfgs from the target triple (no SDK), so a type-check for `aarch64-apple-darwin` on Linux is plausible but unverified.
- `scripts/macos-min.py` builds the examples with default features and checks their C symbols against `FRAMEWORKS`; Metal's headers aren't there.
- CI runs on Ubuntu only (`make check` with clippy for Windows and Linux, `make test`, `make pace` under Xvfb): it never compiles the Metal code. macOS is checked by `make check` / `make test` on a Mac and in the VM.
- `Cargo.toml` `include` packages `/src/**/*.rs` only: a `.metal` file wouldn't reach crates.io.

## Decisions

Decided (the coordinator, 2026-10-31):

- **An optional cargo feature `metal`, off by default.** The default build keeps 13 crates and the readme's "no GPU API, shaders or drivers" stays true; with the feature, 14. `cargo add --optional` declares an implicit feature named `objc2-metal`; `[features] metal = ["dep:objc2-metal"]` replaces it, so the only name is `metal`. A binary built with the feature links Metal.framework even when it draws on the CPU: the CPU baseline is measured once from a default build too (task 6).
- **The harness hook is `#[cfg(feature = "metal")] Harness::render_metal()`**, public under the feature (not `#[doc(hidden)]`), and the parity tests are `#[cfg(feature = "metal")]` too.
- **A new budget part `metal`.**
- **Benchmarks run windowed in the macOS VM only; the host runs headless tests only.**

Taken in this plan (each can be overturned by the person):

- **Draw into the IOSurfaces, not a CAMetalLayer.** Metal renders into an `MTLTexture` made from each of the presenter's IOSurfaces (`newTextureWithDescriptor:iosurface:plane:`, macOS 10.11), waits for the command buffer to complete, and sets the surface as the layer's contents exactly as the CPU path does. Why: the presenter's surface rotation (lazy second and third surface, `starved`), the overlay's transparency, `setFrameSize:`'s synchronous resize, `NIMBO_TRACE` and the headless tests on `CALayer::new()` all stay as they are; memory is the CPU path's surfaces plus the device, not three drawables; the swap is a few lines in `surface.rs` and `view.rs`. The cost: the main thread waits for the GPU each frame (sgui: 0.14–1.93 ms median at 2560×1600), as it now waits for the CPU raster. A `CAMetalLayer` with `presentsWithTransaction` during resize (sgui's path, and what wgpu-based toolkits use) presents asynchronously but replaces the layer, keeps up to 3 drawables (~12.7 MB each at 1100×752 @2x) and can block in `nextDrawable`; it stays a follow-up if the wait shows in the benchmark.
- **Every render target is an IOSurface texture, the harness's too.** `snapshot` renders into a `Surface` of its own and reads it back under `IOSurfaceLock` with the surface's bytes per row, so tests exercise the window's real target and stride and no render target depends on shared versus managed storage. The sampled textures (atlases, images) are `Shared` when the device `hasUnifiedMemory`, else `Managed` (`replaceRegion` works on both); the instance buffer is `Shared` (fine for buffers on every Mac). The VM probe records `hasUnifiedMemory` (task 2).
- **Clip space from the target's whole pixels.** `cpu::Renderer::pixel_size` truncates a fractional size, and the CPU rasterizes at pixel centres of that frame; so the vertex shader maps a point `p` to clip space as `p * scale / (w_px, h_px)` (the target's width and height in pixels), not `p / size` in points. The scissor is `cpu::scissor` (made `pub(crate)`), which clamps to the frame: Metal rejects a scissor past the texture.
- **Full redraw of every frame that changed; an unchanged frame isn't presented.** The GPU draws all of it (no tile hashes, no `prepare`: that CPU work is what the bunnies pay for); a hash of the frame (each layer's clip and instance counts, the instance bytes, the image ids, the size in pixels, the scale, the transparency and a sync generation bumped by an atlas reset or an image change) skips a present equal to the shown one, as the CPU path's empty damage does; the hash is forgotten when the surfaces are dropped (a new size, `idle`). Drawing only the damaged tiles is possible later (an IOSurface keeps its pixels, unlike a drawable) but not needed for the comparison.
- **One frame in flight, waited for.** With the wait above there is one instance buffer (write-combined, grown to a power of two, at least 64 KB), no ring, no semaphore and no completion handler; atlas uploads (`replaceRegion`) never race a frame. After the wait the command buffer's `status` and `error` are checked (below). Each encode-commit-wait and each snapshot runs inside `objc2::rc::autoreleasepool`, so Metal's autoreleased objects don't pile up between run-loop turns.
- **A failed frame falls back to the CPU for good.** If a command buffer ends in error, that surface isn't shown, the window switches to the CPU renderer for the rest of its life and one line goes to stderr with the error. In Metal mode `Presenter::sync` syncs only the Metal renderer, so the CPU renderer holds no atlas or image pixels then: on the switch the text system's atlases are reset (`Atlas::reset` through a crate-private `TextSystem::reset_atlases`, ~5 lines in `text`, so every glyph is rasterized and uploaded again), the Metal renderer hands the images it keeps (their premultiplied pixels, as the CPU renderer keeps them) to the CPU renderer, and the frame is drawn again on the CPU.
- **Shaders compiled from source at the first Metal frame** (`newLibraryWithSource:options:`, `include_str!`), so a build needs no Xcode Metal toolchain (sgui: 3.5 ms with Metal's shader cache), with `MTLCompileOptions.languageVersion` pinned to 2.3 (macOS 11's), so every system compiles the same language. Fast math stays at Metal's default unless parity fails; then `setFastMathEnabled(false)` (deprecated in objc2-metal 0.3.2; its replacement `mathMode` is macOS 15) under `#[allow(deprecated)]`. The device, queue and four pipelines are made once per thread (the main thread in an app, each test thread in the harness), lazily: an app that never draws a Metal window never touches Metal.
- **`shaders.metal` is written from nimbo's `raster.rs`, function by function** (the names `raster.rs` already cites), starting from sgui's file (the person's own project, moved without attribution) with the four fixes in. Its header keeps sgui's credit: per-corner radii and per-side borders follow the approach of Zed's quad shader (`crates/gpui_apple/src/shaders.metal`, Apache-2.0), simplified; no Zed (GPUI), egui or wgpu code is copied, and its comments name `raster.rs` as its twin.
- **Textures:** the coverage atlas `R8Unorm`, the colour atlas and images `RGBA8Unorm`, never `_sRGB` (the data is premultiplied RGBA in sRGB space, sampled as is); each atlas texture is zeroed when made. The atlases start small and grow (the review's lever, needed for the 8 MB target: full-size atlases are 4 + 4 MB per Metal window, as each window has its own text system): nimbo's packer fills shelves across the full 2048 (1024) width, so a texture keeps that width and starts 128 (64) rows high, doubling in height by a blit when an upload reaches past it; a reset keeps its size. The colour atlas is made only with the first emoji.
- **Selection:** `View::new` reads `NIMBO_RENDERER` (beside `NIMBO_TRACE`) and passes the choice into `Presenter::new`; unset or `cpu` keeps the CPU path. When Metal can't be had (built without the feature, no device, a shader that doesn't compile), the window draws on the CPU and one line goes to stderr naming why; when it is used, one line names the device (`nimbo: renderer metal (Apple M2)`, the paravirtual device in the VM), so a benchmark can't measure the CPU path by mistake. `--shot` honours the variable too, so a Metal shot can be looked at.
- **IOSurfaces into Metal without `objc2-io-surface`:** the one selector is sent with `msg_send!` and a local opaque type whose encoding is `^{__IOSurface=}` (objc2 checks encodings in debug builds), from the `CFType` surface `surface.rs` already makes: 14 crates with the feature, not 15.
- **Metal's parts:** `src/platform/macos/metal/` (`mod.rs` the per-thread device and pipelines, `render.rs` the renderer and snapshot, `present.rs` the window path, `shaders.metal`), budget part `metal` in `scripts/size.py`, with `.metal` lines counted (the shader starts with the copyright line and a `//!` doc, both valid MSL comments, so `--map` lists it).
- **macOS 11:** everything used exists on 10.11–10.15 (device, queue, library from source, MSL 2.3, pipelines, IOSurface textures, `hasUnifiedMemory`, `replaceRegion`, blits, scissor, instanced draws, `waitUntilCompleted`, `status`/`error`; `GPUStartTime`/`GPUEndTime` 10.15 for the trace). `MTLCreateSystemDefaultDevice` is the one C symbol: `macos-min.py` gets `Metal/Metal.h` in `FRAMEWORKS` and also builds the examples with `--features metal`, so the guard sees it. Selectors stay for review, listed in the PR.
- **Threads and the busy rule:** the presenter lives in the view's `State` and runs only inside `render()`, which already holds the `try_borrow_mut`; the per-thread device is immutable once made; no Metal callback touches the view. A later asynchronous present (follow-up) would hop to the main queue and reach the view only through its `try_borrow*` helpers, deferring when busy.
- **Memory measured fairly.** `idle()` (every surface but the shown one dropped when the view pauses) is added on the Metal path only, so the CPU path keeps up to 3 surfaces: Metal's footprint is measured with and without it (a scratch build with the call removed, not committed) against the CPU path, so the 8 MB comparison is like for like, and the first frame after an idle pause (a new surface and texture made) is timed against a steady frame.
- **Not changed:** the display link, timers and pacing (`link.rs`), the CPU renderer's drawing, the scene, the public API apart from the feature-gated harness method, Windows and Linux.

## For the benchmark

Once task 6 is done, the benchmark agent builds its bunnies app against this branch with the feature (`nimbo = { path = "/Users/user/Code/nimbo/.worktrees/metal", features = ["metal"] }`, or for nimbo's own examples `cargo build --release --features metal --example <name>`) and runs it windowed in the macOS VM only, the same binary twice: with `NIMBO_RENDERER=metal` and without it (and a default build once, for the CPU baseline without Metal.framework). It checks the first stderr line names the Metal device; `NIMBO_TRACE=1` prints each present (`nimbo: presented <unix ms>`, on the Metal path followed by the encode and GPU-wait milliseconds) for fps and frame time; `MTL_HUD_ENABLED=0` before measuring footprint (`footprint <pid>`); `Ui::last_frame()` gives the view, layout and paint time, so a slow frame can be split into building the scene (the same on both paths) and drawing it. Sprites of one image in a row draw as one instanced call; alternating images draw one call per run, which the benchmark should note if it does that.

## Out of scope

- A GPU path on Windows or Linux (D3D, Vulkan, GL, wgpu): their GPU stacks cost 100+ MB per process (sgui's probes), against the memory goal.
- Metal as the default, or removing the CPU path; text blended in linear light; a CAMetalLayer present; drawing only damaged tiles on the GPU; an asynchronous present.
- Releasing spare surfaces when idle on the CPU path (the same helper would do it; a separate change to the default path).
- The CPU path's ~2 GB peak footprint during a 60 Hz live resize found by the benchmark (new IOSurfaces per size change): a separate issue; the Metal path shares the same surface rotation, so it shows there too until that is fixed, and task 6 records both peaks for it.

## Risks

- Paravirtualized Metal in the VM may lack a feature used here (IOSurface-backed render targets, R8 textures, compiling from source, unified memory) or be slow; task 2's probe finds out before the window work. The VM's GPU numbers say little about a real Mac; windows on the host are out of this plan.
- CI type-checks the Metal code for `aarch64-apple-darwin` on Linux (task 1) but never links or runs it: a link or run-time break shows only in a Mac's `make check` / `make test`.
- Metal device access may be blocked in an agent's sandboxed shell on the host; a test that can't get a device fails rather than skips, and the agent reports it.
- objc2's debug-build encoding check rejects the IOSurface argument if the local type's encoding is off; the fallback is the `objc2-io-surface` feature (15 crates), a decision then.
- Bilinear filtering differs slightly between the GPU and `raster.rs`'s `sample` (the GPU's weights are coarser): the 2% allowance for `shapes`; bunnies at fractional positions sit in that class, hence the share and percentile assertion.
- The wait per frame keeps one frame in flight: if the GPU is slow in the VM, frame time = build + encode + GPU time; the trace's encode/wait numbers show it.
- Each Metal window has its own atlases (up to 4 + 4 MB at full size): many windows multiply that even with growth.
