# File dialogs and dropped files

Done: 2026-10-26

Issue #27, for Wavo's Import button: the system's open and save panels, and files dropped on a window.

- [x] `FileDialog` (open or save: title, types, folder, suggested name), asked by a window (`Ui::file_dialog`), taken by the platform after an event or a frame (`Runtime::take_file_dialog`, as `take_resize`), answered as `Event::FileDialog(Option<PathBuf>)`; the harness answers it (`Harness::file_dialog`), so a flow through the panel is tested headless. Asked by the window rather than by `Main` (as the issue sketched) for that.
- [x] `Event::DragOver`, `DragExit`, `Drop` with the paths; the hover follows the drag, so `cx.hovered(id)` tells where the files would go
- [x] macOS: `NSOpenPanel` / `NSSavePanel` as a sheet (content types from `UTType`, which AppKit loads), the view an `NSDraggingDestination` for file URLs; the NSEvent conversions moved to `macos/input.rs` to keep `view.rs` under 800 lines
- [x] Windows: `IFileOpenDialog` / `IFileSaveDialog` owned by the window, an `IDropTarget` reading CF_HDROP
- [x] Linux: the portal's `FileChooser`, GTK 3's drag destination with `text/uri-list`
- [x] `examples/files.rs` and `tests/files.rs`
- [x] Checked in real windows: macOS (by the owner), Windows 11 ARM64 and Ubuntu 24.04 GNOME on X11 in the VMs (`~/Code/vm`, built on the Mac with `cargo xwin` and `cargo zigbuild`): open with a filter, save with the suggested name, cancel, the zone lit under a drag from Explorer / Nautilus, the drop listed, a drag taken away leaving it as it was. Not checked: Wayland.

## Result

Apps open and save files through the system's panels and take files dropped on their windows on all three OSes, with headless tests through the harness. Budgets raised by whole hundreds after writing the code tight: platform/macos 1800 → 1900, platform/windows 2000 → 2200, platform/linux 2900 → 3000, core 3500 → 3600.
