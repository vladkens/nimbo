# Accessibility, macOS first

Done: 2026-10-26

Screen readers and other assistive tools see a nimbo window as empty: VoiceOver reads nothing, and Voice Control and Full Keyboard Access find no controls. Every competing stack exposes its controls (Handy: a Tauri webview; egui, Slint, Xilem: AccessKit). Wavo-app is a dictation app, and dictation matters to people who can't see the screen. Assessment: `~/Code/notes/nimbo/readme.md` (2026-10-26). The plan was reviewed against the code at `ee5e00c` (2026-10-26) and revised.

## Decisions

- **Own model, no AccessKit.** Its adapters cost +7 crates on macOS, +22 on Windows and +86 on Linux, against nimbo's 13 / 4 / 2. The adapters are written per OS over the platform layer, ported where useful from AccessKit (MIT / Apache-2.0, `~/.cargo/registry/src/*/accesskit_macos-0.27.2`; objc2 0.5 there, 0.6 here: nothing copies verbatim), naming the source file. macOS needs only objc2-app-kit features (`NSAccessibility`, `NSAccessibilityConstants`, `NSAccessibilityElement`, `NSAccessibilityProtocols`), added with `cargo add --features`.
- **Records keyed by `Id`, kept in `Tree`.** A behaviour takes its id before the element exists, and form rows and tooltips name their control from outside it, so records are `(Id, node)` entries in a side list of `Tree` (beside `partial`), cleared with it, joined to the laid-out nodes after layout by id. Extra passes (rehover, partial builds, input-only passes) swap or drop the whole tree, so they neither duplicate nor lose records. The tree nests records under their nearest recorded ancestor (pre-order with `parent` / `end`), floats under their own parent.
- **Roles and states come from the behaviours.** `begin(id)`, which every behaviour calls, takes the role and the disabled state; behaviours add their states (on, focused, a slider's number and range, a field's text). Widgets only refine (a switch is a check box with the switch subrole). So an app that draws its own look over a behaviour is accessible too. A node's name, when none is set, is the text inside it; leaf roles (button, check box, field, link, menu item, tab) hide the text nodes inside them, and plain text elsewhere is static text without any call.
- **Names from context.** `form_row` puts its label and caption in a `Ui::slot`: an unnamed control inside it takes them as its name and description, and the label text isn't read again. `tooltip(target, tip)` sets the target's description. An app names what nothing names (an icon button) with a next-element modifier, `ui.label("Delete")`, consumed like `disabled`.
- **Always recorded, assembled on demand.** Records are a few small structs per control (strings in an arena, as `tree.text`), so they are always kept, and the harness reads them with no activation. The assembled tree and the platform objects are built from the last frame on the first query, which must not come back empty (VoiceOver caches an empty window).
- **Actions go through the existing input paths.** Press: a click on the node's id (as the runtime delivers one, without moving the pointer or the hover), so a click, Space and VoiceOver's press run the same code. Increment and decrement: the arrow commands delivered to the id. Focus and scroll to visible: `set_focus` and the scroll areas' reveal. Set value: the only new widget code, a few lines in the text field behaviour. Nodes behind an open modal dialog are left out.
- **macOS in this PR.** Linux (AT-SPI2 over nimbo's GDBus) and Windows (UI Automation) follow, each its own PR, on the same model.

## Tasks

- [x] 1. The model (`src/ui/a11y.rs`, `impl Ui` there: `ui/mod.rs` and `layout.rs` are at their ~800 lines): `Role` (group, button, check box, switch, radio button, slider, text field, secure text field, static text, link, pop-up button, menu, menu item, tab list, tab, list, row, progress indicator, image, dialog), name, description, value (text, number with min and max, check state on / off / mixed), states (disabled, focused, selected, expanded, modal), the active descendant (a list's cursor row, a menu's highlighted item), actions. Records in `Tree`, the `begin(id)` role, `Ui::label` and the `form_row` slot, assembly with rects in window points clipped to their scroll areas (fully clipped nodes left out), and a text dump for the harness (`Harness::a11y()`). Unit tests.
- [x] 2. Every behaviour and widget sets its role and states: button, icon button, check box, switch, slider, text field (a password field never exposes its text), search field, select / pop-up, segmented control (radio group), tabs, list and rows (selected, cursor), link, progress, badge, menu and items, dialog and buttons, form rows, tooltips. Each example's tests assert the parts that matter (settings: "Open at login, switch, off").
- [x] 3. Actions: `Event::A11y { id, action }`, consumed by the runtime before the app (as `Appearance`), queued like any event while the view is busy. Press, increment, decrement, focus, scroll to visible, set value. Harness `act(id, action)`; tests drive a switch, a slider, a field and a select (press the pop-up, then an item) by actions alone, and a press behind a modal is refused.
- [x] 4. macOS adapter (`src/platform/macos/a11y.rs`; the view's methods are one-liners there, `view.rs` is at 763 lines):
  - A snapshot of the assembled tree (ids, roles, strings, rects in view points, parent and children) copied into the view's ivars after each frame, outside the state borrow. Elements hold a `Weak` to it and their id, and resolve each attribute when asked, never through the runtime (queries arrive in nested run loops). Stale elements answer nil.
  - An `NSAccessibilityElement` subclass per node, kept in a map by `(Id, Role)` so identity holds across frames, with no strong reference to the view.
  - The view: `accessibilityChildren` (built on the first query), `accessibilityFocusedUIElement`, `accessibilityHitTest:`. Top-level elements' parent is the window, as the view is ignored.
  - Elements: role, subrole, label, help, value, min and max value, enabled, focused, selected, selected children, modal, frame in screen coordinates (computed when asked, through the view's `to_screen`), parent, children, `isAccessibilitySelectorAllowed:`; for fields the character count, selected text range, string for a range and insertion point line, from `TextInput`'s UTF-16 ranges.
  - Actions `accessibilityPerformPress`, `…Increment`, `…Decrement`, `setAccessibilityFocused`, `setAccessibilityValue`, sent as events through the view's queue.
  - Notifications, posted in `after_frame`, outside the borrow: focus changed, value changed (the focused node's last), selected rows changed, selected text changed, title changed, element destroyed for removed nodes and at window close, layout changed only when the structure changed (never per animation frame).
- [x] 5. Check in the macOS VM (`~/Code/vm`, `./vm prepare macos --test-host`, `./vm exec macos --gui` runs trusted for Accessibility): an AX dumper in Swift built on the host (`xcrun swiftc -target arm64-apple-macos14`, the guest has no toolchain), driven by `scripts/ax-check.py` (copies it and an example over, starts the app, dumps with one retry, presses, quits). Dump the settings and gallery examples; `AXPress` a switch, `AXIncrement` a slider, set a field's value, and see each change in the next dump. A pass with VoiceOver itself comes from people who use it, through issues.
- [x] 6. Docs and budgets: the readme's features, AGENTS.md's toolkit lines; budgets recorded in the PR: a new `a11y` part (400, with `"ui/a11y": "a11y"` in `PARTS`), widgets 3300, core 3700, platform/macos 2500. With it, the two defects task 5 saw: a modal dialog leads assistive technology to its default button, and the gallery names its second switch, its slider and selects.

## Result

nimbo windows are accessible on macOS with no new crate (20 in the tree before and after): every behaviour records its role, name, value and states by id (`src/ui/a11y.rs`), the tree is assembled from the last frame on demand, and `src/platform/macos/a11y.rs` exposes it as `NSAccessibilityElement`s with actions (press, increment, decrement, focus, set value) through the input paths and notifications from a diff after each frame. Harness tests assert each example's tree with `Harness::a11y()` and drive controls with `Harness::act`; `scripts/ax-check.py` checked the settings and gallery examples through the AX API in the macOS VM. A modal dialog keeps the keys on its backdrop (no ring, as an NSAlert) and shows its default button focused to assistive technology (`Ui::a11y_focus`), giving the focus back on close. Budgets raised: a11y 400 (new part), widgets 3200 → 3300, core 3600 → 3700, platform/macos 1900 → 2500. Left for later: Windows (UI Automation) and Linux (AT-SPI2), nodes scrolled out of view left out of the tree; how VoiceOver users find it, through issues.
