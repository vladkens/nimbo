# Native context menus

Done: 2026-10-30

Goal: a context menu is the OS's own menu, shown at the pointer and free to go past the window's edge (`NSMenu popUpContextMenu:withEvent:forView:`, `TrackPopupMenuEx`, `GtkMenu` with `gtk_menu_popup_at_pointer`), so the fields' edit menu stops being clipped to the window and stops looking foreign on Windows; an app attaches a menu to any element. Agreed in `~/Code/notes/nimbo/roadmap.md`, phase 3 item 1 (2026-10-27/29). Select popups and `Ui::menu` buttons keep their drawn menu; the harness keeps a drawn menu for every context menu, so tests and shots work as now.

## Decisions

- One model for the tray and context menus: `Menu`/`Item` move from `src/tray/mod.rs` to `src/menu.rs` (re-exported as `nimbo::{Menu, Item}`, `tray::{Menu, Item}` kept), counted in `app/shared` (`PARTS` in `scripts/size.py`). New on `Item`: `Item::header(label)` (a section title, never chosen) and `.destructive()`. Existing: separator, `checked`, `key` (shortcut label), `enabled`, `submenu`. Submenus are in: all three tray builders already make them.
- API (`src/ui/containers/menu.rs`): `ui.context_menu(id, || menu) -> Option<String>` on any element: a secondary press on `id` or inside it (the innermost element with a menu wins, by the last frame's parent chain) builds the menu (the closure runs only then) and opens it at the pointer; the chosen item's id comes back as `Event::Menu { on: Id, item: Option<String> }` (`None`: dismissed), delivered to `on` in a view pass, where `context_menu` returns `Some(item)`, and to `App::event` when no view took it. `ui.context_menu_at(id, at, menu)` is the same for a point a behaviour already has (the field's).
- Native or drawn: the platforms call `Runtime::set_native_menus(true)`; then `context_menu` stores the request in `UiState::context_menu: Option<(Id, Point, Menu)>`, taken by `Runtime::take_context_menu()` exactly as `take_file_dialog` is. Otherwise (the harness) it draws the menu with `menu_popup_at` from the model: check column, header in secondary text, shortcut right-aligned, destructive in `theme.danger`, a submenu's items flattened under its label as a header. Item ids in the drawn menu are `id.key(item.id)`.
- When it opens: on the secondary press on macOS and Linux (as AppKit and GTK do), on the release on Windows (`WM_CONTEXTMENU` follows `WM_RBUTTONUP`, as Explorer and the Edit control do), by `ui.os`; the same rule for fields, `context_menu` and `List`.
- Fields: `EditMenu::items() -> Menu` (ids `cut`, `copy`, `paste`, `select_all`, a separator before Select All, no shortcut labels: AppKit's, Win32's and GTK's text menus show none); `Ui::edit_menu` calls `context_menu_at(b.id.key("edit"), m.at, menu)` and maps the choice to `field_command`; `FieldState::menu_open` stays true until `Event::Menu` answers, so the field keeps its focus look.
- `List`: a secondary press on a row outside the selection selects that row alone, on one inside it keeps the selection (Finder's rule), then the app's `context_menu(list.id, || menu_for(&sel))` reads the selection the press just made.
- The OS loop: the popup runs outside the window's borrow (AGENTS.md: `try_borrow*` only), like the file panel. macOS and Windows block in a tracking loop: macOS frames go on (the display link is in `NSRunLoopCommonModes`), Windows' from the modal timer (`modal(1)`/`modal(-1)`, as the tray's `show`). A request while one is open is answered `None` (macOS, Windows) or replaces it (Linux, which doesn't block).
- Accessibility: a native menu is the OS's (AXMenu, MSAA, ATK), so the model records nothing for it; the drawn fallback keeps `Role::MenuItem` as now. Opening a context menu from VoiceOver (AXShowMenu) or the keyboard (Menu key, Shift+F10) is a follow-up (the `a11y` budget is full).
- Destructive: AppKit, Win32 and GTK 3 menus have no destructive style as far as known; check the current AppKit docs (`NSMenuItem`) at task 3 and date it in the code; where there is none it shows as a plain item and only the drawn menu colours it.

## Risks

- Wayland: `gtk_menu_popup_at_pointer` needs a trigger event whose serial the compositor still accepts for the popup grab; the press reaches the view a frame later (the menu is asked for in the next build), so a copied press of a few ms is kept; if a compositor refuses it, the release's event is the fallback. On Wayland the popup takes keyboard focus, so the window may get a focus-out (the field dims its selection); seen in the VM check.
- macOS: `popUpContextMenu` with a kept event whose time is a frame old; and the chosen item's action arriving after the call returns (task 3 checks it).
- Windows: Win32 popup menus stay light in dark mode (as the tray's today) without the undocumented `uxtheme` ordinals; not in scope, noted for a follow-up.
- Nested loops: a callback during tracking (a timer, a wake, a second launch's command) must find the window free: no borrow is held across the popup, and events that come while busy queue as now.
- Budgets are near full on every platform and the core; the estimates above may need another hundred somewhere.

## Result

A context menu is the OS's own on macOS, Windows and Linux (X11 and Wayland), at the pointer and past the window's edges, for any element (`Ui::context_menu`), a field's edit menu and a list's rows; the harness draws it from the same model, which the tray shares (`src/menu.rs`). Checked in the VMs on macOS 27, Windows 11, Ubuntu 24.04 on X11 and GNOME Wayland, and KDE Plasma 5.27 Wayland; `make pace` passes on every backend whose loop changed. Budgets: `widgets` 3400→3500, `app/macos` 1800→1900, `app/linux` 2400→2500 (the core raise dropped: main's 4000 since #54). Left: the AutoFill defaults unchecked in a VM (above); Windows' menus stay light in dark mode; opening a menu from VoiceOver or the keyboard; while a GTK menu is open the window has no focus, as in GTK's own apps.
